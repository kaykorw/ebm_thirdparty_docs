Standard codes are the shared lookup tables RRA maintains for tax types, packaging, payment methods, stock movement types, and related classifications. Before you issue invoices, your application should understand which codes VSDC will accept for your taxpayer.

Kayko exposes two layers:

1. **Static convenience tables** under [`GET /constants/*`](/api/constants), stable enumerations shaped for integrators (labels, rates, directions).
2. **Live code sync** under **`/codes`**, pulls the taxpayer’s current code classes from VSDC (`code/selectCodes`) and caches them. Use this when you need the device’s actual catalog (including tourism-related codes) rather than only Kayko’s static lists.

Send `x-tin` and `x-branch-id` on every route below. Kayko resolves your business VSDC URL after Enable EBM; do not put `ebm_url` in the body. Authenticate with a business API key (any scope today; the selectable `codes` scope covers this domain when you create a key).

## Sync codes from VSDC

`GET /codes`

This route asks VSDC for code classes and detail rows that changed after your sync cursor. It is the Kayko equivalent of spec §3.3.2.1 (`/code/selectCodes`).

**Required header:** `x-last-request-date`, fourteen digits `YYYYMMDDHHmmss`. For a first full pull use `20000101000000`. After a successful sync, advance the cursor you store for **this** endpoint (do not share it with items or purchases). See [Data Synchronization](/concepts/data-sync) and the [Glossary](/reference/glossary) entry for last request date.

Successful responses use Kayko’s mapped shape `{ message, data, meta? }` with human-oriented code fields (for example class code, class name, nested codes with names and optional user-defined rate fields). An empty delta is not a hard failure, treat an empty `data` array like “nothing new,” consistent with upstream result `001`.

```bash
curl -X GET "{{baseUrl}}/codes" \
  -H "Authorization: Bearer sk_live_YOUR_SECRET" \
  -H "x-tin: 100027060" \
  -H "x-branch-id: 00" \
  -H "x-last-request-date: 20000101000000"
```

## Read cached codes

`GET /codes/cached`

Returns the last successfully cached code set for the TIN without calling VSDC again. Use this for UI dropdowns when you already synced recently. If the cache was never populated, Kayko returns an error such as `EBM_CODES_CACHE_MISS`, call `GET /codes` first.

Tenant headers `x-tin` and `x-branch-id` are required; `x-last-request-date` is not.

## Tourism tax settings

Live devices validate **tourism header rates** (`taxRtF`, `taxRtTt`) on every sale. Kayko stores a per-TIN preference so your POS does not hard-code fragile numbers.

### Get tourism settings

`GET /codes/tourism`

Returns whether this TIN is treated as tourism-oriented, any stored rate overrides, the active strategy (`non_tourism_null`, `tourism_catalog`, or `override`), and a short setup hint.

### Update tourism settings

`PUT /codes/tourism`

| Field | Required | Description |
|-------|----------|-------------|
| `tourism_tax` | Yes | Boolean. When true, sales without explicit overrides use catalog tourism rates (usually 3%). When false, Kayko sends null tourism header rates unless overrides exist. |
| `tax_rate_f` | No | Optional override for upstream `taxRtF` (0–100, max two decimals). |
| `tax_rate_tt` | No | Optional override for upstream `taxRtTt`. |

```json
{
  "tourism_tax": false,
  "tax_rate_f": null,
  "tax_rate_tt": null
}
```

If a live device rejects null rates for your TIN, set numeric overrides only after your VSDC administrator confirms the programmed values. Until then, treat the correct pair as **unconfirmed, pending RRA clarification**.

You may also pass `tourism_tax`, `tax_rate_f`, and `tax_rate_tt` on an individual [`POST /sales`](/api/sales) request; stored `/codes/tourism` values cover the default for that TIN.
